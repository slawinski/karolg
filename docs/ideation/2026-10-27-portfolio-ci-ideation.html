Engineering choices / portfolio

Better CI, with a small maintenance bill.

Date: 2026-10-27 · Topic: portfolio-ci · Scope: this codebase

Focus: What options do we have to improve this portfolio’s CI, and which should we take?

Recommendation: take the balanced option.

Choose early feedback, a deterministic real-page visitor smoke test, and retained failure evidence (ideas 1–3). Keep Chromium and WebKit coverage. Consider sharing production-build setup once compatibility is established. Add performance reports before performance gates; keep recovery rehearsals selective.

Lean: 1 + 3. Balanced: 1 + 2 + 3. Extended: selected additions from 4–6. The balanced option closes a real integration gap without creating a large testing platform.

Codebase Context

The baseline is already substantial: one GitHub Actions job runs Node tests, Chromium and WebKit component tests, typechecking, migration, and two production-runtime verifiers. Those verifiers build and start Next.js against disposable data. A separate build check is therefore already covered indirectly.

The clearest friction is ordering: typecheck follows FFmpeg setup and both browser suites. Both production verifiers independently build. Component browser tests replace Next links and images, while the real-navigation script is outside CI. The workflow does not upload diagnostic artifacts.

Deployment uses a persistent Next server with SQLite and media storage. Populated-schema migration upgrade/rollback tests already exist; recovery’s remaining distinct question is whether restored data and media work together. Existing performance reports are historical local observations, not current production measurements.

Evidence came from repository scans and independent source verification. Official GitHub Actions caching and concurrency documentation was consulted through Context7. Broad web search was unavailable. No CI runs were benchmarked, so speed and runner-cost benefits remain unmeasured. No application tests were executed for this advisory analysis.

1. Earlier answers with lean workflow hygiene

Get typecheck results before browser provisioning can delay them. Use a modest number of independent checks where timings justify the extra setup. Add pnpm-store caching and cancellation of superseded PR runs, with explicit token permissions and clear check names.

Axis
Feedback speed and execution cost
Basis — direct + external
.github/workflows/ci.yml:25–42 places pnpm typecheck after FFmpeg setup and both browser suites. The workflow does not configure cache or concurrency. GitHub documents pnpm caching through setup-node and workflow/ref cancellation groups.
Rationale
This removes avoidable waiting and stale work without requiring new product tests. Distinguish time to first useful failure from total duration and runner minutes. Start here.
Downsides
More jobs repeat install/setup and may increase runner minutes. Caching does not eliminate installs. Cancellation policy needs care if deployment is later added; separate browser jobs are an option to measure, not an automatic requirement.
Confidence
95%
Complexity
Low for ordering/cache/cancellation; Medium if splitting jobs.

2. One seeded production visitor journey

Use a small synthetic portfolio to test the actual Next.js experience: home → story → back → contact at mobile and desktop sizes. Reuse navigation and reduced-motion checks, adding focused keyboard/focus and automated accessibility checks. Keep component tests for detailed behavior.

Axis
Real visitor journey coverage
Basis — direct
PRODUCT.md:20 defines success through understanding, exploring stories and contacting Carla. vitest.browser.config.ts:9–12 substitutes Next image/link implementations. scripts/verify-public-navigation.mjs:33–168 tests real navigation but is not run by CI.
Rationale
This is the strongest coverage addition: certify the assembled experience and the portfolio’s intended outcome. The product’s accessibility requirements at PRODUCT.md:118–120 give the focused checks a clear purpose.
Downsides
The existing script is not plug-and-play: it assumes tall pages, video, delayed poster behavior, and /work/d. Fixtures must supply those capabilities or the script must accept a manifest. Avoid arbitrary sleeps and a broad breakpoint matrix. Automated accessibility scans cannot prove full WCAG conformance.

Complexity
Medium

3. Failure evidence you can actually inspect

Retain browser failure screenshots, available traces, relevant server output and a small report naming the route, viewport and failed step. Add a concise test summary with unexpected skips, rather than a standalone reporting subsystem.

Axis
Trustworthy results and failure diagnosis
Basis — direct
The full .github/workflows/ci.yml has no artifact upload. scripts/verify-homepage-scroll.ts:222–233 already demonstrates project-specific failure state, failure.png and evidence.json. That script itself is not currently invoked by CI.
Rationale
Scroll, readiness and media failures are easier to understand when the failing state survives the runner. Attach evidence collection to checks that actually execute; existing local patterns make this cheaper to design.
Downsides
Artifacts need bounded retention and reliable capture during failure. A screenshot alone rarely explains the preceding sequence. Current FFmpeg/ffprobe preflights already fail on missing tools; there is no demonstrated false-green video run to justify a separate coverage-receipt system.
Confidence
96%
Complexity
Low to Medium, depending on capture support.

4. One compatible production-test harness

Explore sharing the build, server lifecycle and deterministic fixtures across slug, social-metadata and visitor scenarios. Keep the important guarantee that CMS changes made after build are visible without redeployment.

Axis
Feedback speed and execution cost
Basis — direct
scripts/verify-photoshoot-slugs.ts:11–40 and scripts/verify-social-metadata.ts:10–39 independently configure disposable environments, migrate, build and start. README.md:59–62 warns that verification writes shared .next output.
Rationale
A common lifecycle could eliminate duplicated builds and make future production checks cheaper to add. This ranks below immediate workflow improvements because safe reuse requires more reasoning than caching.
Downsides
Each script currently uses distinct database/media paths, secrets and public origins. Reuse must reconcile build-time assumptions and isolate scenario state. Do not parallelize scripts that write the same .next directory. Avoid turning a useful helper into a large test framework.
Confidence
83%
Complexity
Medium

5. Report-first mobile performance checks

Reuse the controlled cold-load experiment for media/loading changes or scheduled runs. Retain repeated samples, raw results and route-specific measurements; consider paired base/candidate comparisons when the signal warrants their cost. Promote only stable, actionable regressions to blocking checks.

Axis
Ongoing quality and change safety
Basis — direct + reasoned
docs/verification/public-mobile-cold-load.md:13–19 defines constrained viewport/network/CPU measurements and repeats. Lines 196–209 report historical homepage LCP of 2789 ms and explicitly limit the claim to local samples. PRODUCT.md:116 makes performance part of the aesthetic.
Rationale
Media and motion changes can erode the first impression while functional tests stay green. Existing measurement work provides a credible starting point, not a ready-made universal threshold.
Downsides
Hosted-runner noise and base/candidate setup add expense. Synthetic fixtures improve repeatability but may not represent real content weight. Keep absolute targets and change deltas distinct. The custom script’s blocking metric is not Lighthouse TBT; lab results are not CrUX.
Confidence
82%
Complexity
Medium to High

6. Selective paired-volume recovery rehearsal

For storage or migration-sensitive changes, restore synthetic persisted database and media together, boot the candidate, and check that a representative public story and its assets remain usable. Consider a scheduled rehearsal if these changes become frequent.

Axis
Ongoing quality and change safety
Basis — direct + reasoned
README.md:155–157 identifies shared data/media volumes and paired restoration. src/lib/social-image-migration.integration.test.ts:25–68 already checks populated-schema upgrade/rollback, so the additional value is serving restored media with restored records.
Rationale
Accumulated portfolio content is worth preserving. This targets an operational boundary clean installs and database-only migration tests cannot establish.
Downsides
Versioned historical fixtures need maintenance. A synthetic rehearsal does not prove real backups are complete or recoverable. This is a selective later investment, not a default requirement on every presentation-only PR.
Confidence
76%
Complexity
High
